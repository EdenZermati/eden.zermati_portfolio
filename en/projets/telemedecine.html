Project question

How can laboratory test results be shared while giving each user access rights suited to their role?

Educational project

Context

This project builds on eight tutorials for a school-related web service. I adapted that starting point to laboratory test results. The task involved changing the database and access rights while protecting sensitive information.

Data model

The MySQL database links users to examinations and their results. It distinguishes patients from doctors and stores the permissions associated with each role.

See the diagrams and design choices

The database contains seven tables.

UserPatientDoctorExaminationExamination resultAccess rightPermission

A common structure for patients and doctors

The first model used user categories. This created redundancy and made the relationship with the treating doctor harder to manage. I changed the model so Patient and Doctor share the User table’s key. Each patient is also linked to a treating doctor. This relationship limits the records a doctor can access.

Health identifiers kept separate from technical keys

Initially, the INS patient identifier and RPPS healthcare professional identifier served as database keys. I replaced them with a technical key called Id_Utilisateur for relationships between tables. INS and RPPS were kept as encrypted attributes.

Approach

I organised processing so requests and permissions are checked before database access. Sensitive data is encrypted at rest and decrypted for authorised reading.

See the six steps and technical details

  1. Defining roles and operations

    We defined three roles with different permissions. Patients read their own results. Doctors read their patients’ results. The laboratory has the read and write operations provided in the project.

    These rules formed the basis of the conceptual and then the logical data model.

  2. Encrypting sensitive information

    I used Fernet in an initialisation script to encrypt sensitive columns. These included names, login identifiers, INS and RPPS. Sex, date of birth and result values were also encrypted. The keys were kept in a protected file.

  3. Preparing API routes

    The file .htaccess rewrites URLs of the form /results/{INS}/{Id_Examen} to the main program results.py. This program handles GET, POST, PUT and DELETE.

  4. Validating requests

    I separated checks for missing parameters from checks of their validity. These cover the URL, headers and request body. Another check prevents adding a result that already exists.

    This structure helps identify errors before changing the database and return an appropriate message.

  5. Checking identity and permissions

    Authentication uses HTTP Basic. This mechanism must be used with HTTPS to protect communications. After authentication, the checks establish whether the user’s role permits the requested operation on that record.

  6. Structuring responses and debugging

    JSON responses contain the fields CODE and TEXT as well as DATA. Messages distinguish errors from successful requests. I added diagnostic output to follow the processing steps and locate problems across the 20 Python files.

Understanding the scenario

Initially record A contains the value 42 and record B has no result. POST creates a value of 42. PUT replaces it with 43. These numbers have no clinical meaning. Changes are temporary and disappear when the page is reloaded.

Tests performed

I manually tested all four methods with the RESTED extension using the laboratory role. It was the only role with all permissions. The tests covered reading, adding, updating and deleting results.

What I learnt

Encryption led me to rethink the database keys during the design stage. I also learnt to separate request checks to understand errors more easily. With 20 Python files, diagnostic output helped me follow each processing step.

See possible improvements

One next step would be to use LOINC codes to identify examinations through a vocabulary shared by laboratories. This would make exchanges between systems easier.

I would also add automated tests alongside the manual tests. Other possible improvements include password hashing, token-based authentication and access logging.
