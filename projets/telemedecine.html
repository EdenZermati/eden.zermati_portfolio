Problématique

Comment partager des résultats d’examens biologiques en donnant à chaque utilisateur les droits adaptés à son rôle ?

Projet pédagogique

Toutes les données utilisées pour les tests et la simulation sont fictives.

Contexte

Ce projet prolonge huit tutoriels consacrés à un web service scolaire. J’ai repris cette base pour l’adapter aux examens biologiques. Il fallait faire évoluer la base de données et les droits d’accès tout en protégeant les informations sensibles.

Ma contribution

Le modèle de données a été conçu avec deux camarades. J’ai adapté les routes et les traitements Python ainsi que les contrôles des requêtes. J’ai ensuite testé les quatre méthodes HTTP avec RESTED.

Modèle de données

La base MySQL relie les utilisateurs aux examens et à leurs résultats. Elle distingue les patients des médecins et conserve les droits associés à chaque profil.

Voir les schémas et les choix de conception

La base comporte sept tables.

UtilisateurPatientMédecinExamenRésultat d’examenDroitAutorisation

Une structure commune aux patients et aux médecins

Le premier modèle reposait sur des catégories d’utilisateurs. Cette organisation créait des redondances et compliquait la relation avec le médecin traitant. J’ai fait évoluer le modèle pour que Patient et Médecin partagent la clé de la table Utilisateur. Chaque patient est aussi rattaché à un médecin traitant. Ce lien sert à limiter les dossiers accessibles au médecin.

Des identifiants de santé séparés des clés techniques

Au départ l’INS et le RPPS servaient de clés dans la base. J’ai utilisé une clé technique nommée Id_Utilisateur pour les relations entre les tables. L’INS et le RPPS ont été conservés comme des attributs chiffrés.

Méthode

J’ai organisé les traitements pour vérifier les requêtes et les droits avant d’accéder à la base. Les données sensibles sont chiffrées au stockage puis déchiffrées pour une lecture autorisée.

Voir les six étapes et le fonctionnement technique

  1. Définir les profils et les opérations

    Nous avons défini trois profils avec des droits différents. Le patient consulte ses résultats. Le médecin consulte ceux de ses patients. Le laboratoire dispose des opérations de lecture et d’écriture prévues dans le projet.

    Ces règles ont servi de base au modèle conceptuel puis au modèle logique des données.

  2. Chiffrer les informations sensibles

    J’ai utilisé Fernet dans un script d’initialisation pour chiffrer les colonnes sensibles. Cela concernait les noms et les identifiants de connexion ainsi que l’INS et le RPPS. Le sexe et la date de naissance étaient aussi chiffrés avec les valeurs des résultats. Les clés étaient conservées dans un fichier protégé.

  3. Préparer les routes de l’API

    Le fichier .htaccess réécrit les adresses de la forme /results/{INS}/{Id_Examen} vers le programme principal results.py. Ce programme prend en charge les méthodes GET et POST ainsi que PUT et DELETE.

  4. Valider les requêtes

    J’ai séparé les contrôles de présence des paramètres et les contrôles de validité. Ils portent sur l’adresse et les en-têtes ainsi que sur le corps de la requête. Un autre contrôle empêche d’ajouter un résultat déjà attribué.

    Cette organisation permet de repérer les erreurs avant de modifier la base et de renvoyer un message adapté.

  5. Contrôler l’identité et les droits

    L’authentification repose sur HTTP Basic. Ce mécanisme doit être utilisé avec HTTPS pour protéger les échanges. Après l’authentification les contrôles vérifient si le rôle permet l’opération demandée sur le dossier concerné.

  6. Structurer les réponses et déboguer

    Les réponses JSON contiennent les champs CODE et TEXT ainsi que DATA. Les messages permettent de distinguer les erreurs des requêtes réussies. J’ai ajouté des affichages de contrôle pour suivre les étapes et localiser les problèmes dans les 20 fichiers Python.

Le parcours d’une requête

Requête HTTP→ .htaccess→ results.py→ Contrôle des paramètres et des droits→ Base MySQL chiffrée→ Réponse JSON
MéthodesGET pour lire. POST pour ajouter. PUT pour modifier. DELETE pour supprimer.
Adresse/results/{INS}/{Id_Examen}

Comprendre le scénario

Au départ le dossier A contient la valeur 42 et le dossier B ne contient aucun résultat. POST crée une valeur de 42. PUT la remplace par 43. Ces nombres n’ont aucune signification clinique. Les changements sont temporaires et disparaissent au rechargement de la page.

Tests réalisés

J’ai testé manuellement les quatre méthodes avec l’extension RESTED en utilisant le profil laboratoire. Ce profil était le seul à disposer de tous les droits. Les tests ont porté sur la lecture et l’ajout ainsi que sur la modification et la suppression des résultats.

Ce que je retiens

Le chiffrement m’a amenée à revoir les clés de la base dès la conception. J’ai aussi appris à séparer les contrôles des requêtes pour mieux comprendre les erreurs. Avec 20 fichiers Python les affichages de contrôle m’ont aidée à suivre les traitements étape par étape.

Voir les pistes d’amélioration

Une première piste serait d’utiliser les codes LOINC pour identifier les examens avec une nomenclature commune aux laboratoires. Cela faciliterait les échanges entre systèmes.

Je compléterais aussi les tests manuels par des tests automatisés. Les autres améliorations envisagées concernent le hachage des mots de passe et l’authentification par jetons ainsi que la journalisation des accès.
